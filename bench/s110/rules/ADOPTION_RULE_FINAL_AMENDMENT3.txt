CHANGE: D4 ("ON X == ON H and ON X == OFF H", request by request over the batched pass) is REPLACED by D4':
  D4'(a) KV BYTE EQUALITY. In one separate ON process per gated profile (spec, ns256), driven by the frozen check tools
         (chk_driver.py, chk_worker.py; md5s recorded in ADOPTION_RULE_FINAL_AMENDMENT3.md5 before the first gate boot,
         AFTER the negative control below is added), the 85 det prompts in greedy run passes C, H, X; every block loaded
         from the CPU tier in pass X is byte-identical (per-region digest on every rank, ALL KV groups, for spec including
         the draft's groups) to its CPU tier copy and, where a pass-H GPU-resident copy exists, to that copy.
         NEGATIVE CONTROL (mandatory, same process): one byte of one tier block is corrupted before a restore and the
         compare MUST report that block as a mismatch; otherwise D4'(a) is ARTIFACT.
  D4'(b) SINGLE-STREAM EQUALITY on a FIXED request list: all 85 det requests in greedy, and all 85 in seeded t1k64
         (seed 1000 + request index), each request ALONE: cold, then pass H (GPU hit), GPU-only reset after the stores
         drained, pass X (tier hit); token ids identical H vs X for every request (and logprobs where requested); for spec
         also the accepted and drafted token counts identical H vs X per request.
  D4' PASS = (a) and (b) hold. If the bytes differ anywhere (a), that is a connector bug: D(that profile) FAILS and no
  further amendment is allowed. D4'(b) failing for any request also FAILS D.
UNCHANGED: D1 (ONa == ONb and OFFa == OFFb in every pass INCLUDING pass X: the guard against timing-dependent load
completion), D2, D3, D5, the ARTIFACT/retry clause, and every other gate. Scope: the ns256 evidence motivates D4'; the spec
profile earns D4' only by passing it inside the gate (15 groups incl. the draft's; v0.33.0 changed the store
finalization and the DFlash trailing-block drop; spec X-vs-H batch differences rose from 4 to 13 of 85).

HARNESS FIX (not a rule change; recorded here because e2e_s110.py is a frozen gate tool): the D(spec) ARTIFACT of the 0.32.0
run (both ON processes exited rc=1) was the driver's own reset retry loop: after a pass, its 16-token retry request leaves
a finished-request store pending in the connector (4 blocks on 0.33.0), Scheduler.reset_prefix_cache checks the GPU pool
before the connector reset releases that store, and the next retry re-pins: a livelock. e2e_s110.py is patched minimally
(the retry probe uses <= 8 tokens, i.e. no full block, nothing to store; or one idle engine step before the full reset);
its new md5 goes into ADOPTION_RULE_FINAL_AMENDMENT3.md5 before the first gate boot, with two proofs: (1) a spec ON process
completes all 12 passes with the patched driver; (2) an OFF boot gives identical token ids with the patched and the
unpatched driver. The scheduler ordering quirk is documented (docs/s110_numa_offload.md), not changed in vLLM.
